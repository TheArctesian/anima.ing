## Effect

On Linux, with the daemon in its systemd user unit, no person can start a thread, answer a request or raise the
limit: not from a terminal, and very likely not from the page Code of the desktop application. A daemon that a
person starts in a terminal is not affected.

## Cause

Measured on `pop-os`.

- `of_an_agent` (`crates/daemon/src/threads/runner/peer.rs`) reads the mark of the thread in the environment of the
  client first (`mark_of` in `crates/daemon/src/threads/marker.rs`, `/proc/<pid>/environ`). An environment that
  cannot be read makes the client an agent (R-315).
- The user unit (`crates/daemon/src/units/render.rs`) has `ProtectHome=read-only`, `ProtectSystem=strict` and
  `PrivateTmp=yes`. The manager of a user has no right to make a mount namespace, so for each of these options
  systemd also puts the service in a user namespace of its own.
- From such a namespace the system refuses `/proc/<pid>/environ` (permission denied) for each process outside it.
  `/proc/<pid>/cgroup`, `/proc/<pid>/cmdline`, `/proc/<pid>/uid_map` and `ps` still read. The same is true for a
  plain `unshare -U`:
  - `systemd-run --user --scope --quiet sleep 40 &`, then
    `systemd-run --user --wait --pipe --quiet -p ProtectHome=read-only sh -c 'wc -c < /proc/<sleep>/environ'`:
    permission denied. With no `-p` option it reads.
  - From the unit, the `uid_map` of the outside process reads `0 4294967295 4294967295`; that of a process of the
    unit reads `1000 1000 1`, and that of a process in a namespace that the unit made (`unshare -U -r`) reads
    `0 1000 1`. The environment of these last two reads.
- So each client of the person is outside the namespace of the runner, its environment cannot be read, and the
  runner refuses it before the check of its group. That check would have said "person": the group of the client
  (`app.slice/app-com.anthropic.Claude-….scope`, or the scope of a terminal) is not the group of the runner
  (`app.slice/anima-daemon.service`).

## Correction

On the branch `fix/peer-environ-userns`:

- [x] When the environment of the client cannot be read, the runner reads the `uid_map` of the client. If a line
  names a user ID that the namespace of the runner does not have (the system writes it as 4294967295), the client
  is in a namespace above the runner's. Then the client goes on to the checks of the tree and of the group, as a
  client without the mark. In each other case an environment that cannot be read still makes the client an agent.
- [x] Why this cannot pass an agent: each process below the holder is in the namespace of the runner or in one
  that such a process made. A process cannot enter a user namespace above its own, and a namespace below the
  runner's holds only user IDs of the runner's. So a client whose namespace holds an ID that the runner's does not
  have is not below the holder, and did not take the mark from it. A process of an agent that keeps the group of
  the runner (`anima-daemon.service`) is still refused by the check of the group.
- [x] The test `thr_049_a_client_above_the_namespace_of_the_runner_is_the_person` starts the runner part of the
  test program in a user namespace of its own (`unshare -U`) and asks it about the test, which is outside. It
  fails without the correction ("environment hidden true, of an agent true"). It is skipped, with a line that says
  so, where the system makes no user namespace.
- [ ] HT-176: the check with the real unit on `pop-os`.

What this does not change: on a Mac and on a daemon that a person starts in a terminal, the runner reads the
environment as before. The known limits of R-315 stay.

## For the operator: the text of R-315

R-315 says that "a process whose environment cannot be read" is taken for an agent. After this correction, on
Linux, a client whose environment cannot be read only because it is in a user namespace above the runner's is not
taken for an agent for that reason; it is still taken for an agent when it is below the holder or has the group of
the runner. The aim of R-315 stays: an agent does not answer its own approval, and when the runner cannot tell, it
refuses. A process outside the namespace of the runner can carry the mark only if an agent asked a program that is
not below the holder to start it with the mark, which R-315 already lists as possible.

Proposed addition to R-315, for the operator to accept or reject: "On Linux, a client in a user namespace above
the namespace of the runner (its `uid_map` names a user ID that the runner's namespace does not have) cannot be
below the holder; when only its environment cannot be read, it goes on to the check of its group."

The other way to correct the defect is to remove `ProtectHome=`, `ProtectSystem=` and `PrivateTmp=` from the user
unit, so that the daemon has no user namespace. It is not proposed: these options hide folders from the daemon
(MET-019, `crates/daemon/src/units/sandbox.rs`).
