A mockup is a static HTML file that shows a layout before or beside the application. Each mockup has one record in [records/](records/): a file with the six fields of its row. The table under "Index" is generated from the records by `bun run quality:register`; do not change it by hand. `bun run quality:documents` fails when an HTML file in this folder has no link in the table, when the table is not the one that the records give, or when a link in a record does not resolve (PLN-017).

## Rules (PLN-019)

- A mockup and its screens must agree. A commit that changes the layout of a screen in the field "Screens" of a record changes the mockup in the same commit and writes the commit of the comparison in the field "Compared" of the record. Then run `bun run quality:register`.
- One record for each mockup, so two branches that compare different mockups change different files and do not conflict. A new mockup gets a new record in `records/`, named for its folder (`records/<folder>.md`) or for its file (`records/<name>.md`); copy the form of a record that exists.
- At a merge into `dev` the merge script settles the records (`quality/src/merge/mockups.ts`): when both sides changed one record, it keeps the record whose comparison is at the later commit; then it writes the table again, and the document gates on the merge commit check the comparison that it kept. A branch that still changes the table of before the records needs no hand: each row that it changed becomes its record at the merge.
- If the commit cannot change the mockup, it writes the difference in the column "Differences". A difference is a defect: correct the mockup or the screen.
- Before a screen is built, the approved mockup is correct. After the screen is built, the two must agree, and the plan in the column "Owner" says which one a change starts in.
- A mockup takes its colours, sizes and motion from the design tokens (`design/tokens/`). It does not hold a second set of values.
- The states are: Proposed (the operator did not approve it), Approved (approved, and the screens are not all built), Built (the screens are built and were compared), Superseded (a newer mockup replaces it; delete the file in the next commit that touches it).
- A mockup of an idea is in the folder of the idea (`docs/ideas/`), not here (PLN-018).
- To compare: open the mockup and the screen of the application at the same size, in the light and the dark appearance, and look at the layout, the order of the parts, the text and the sizes. Then write the short hash of the commit that you compared, in backticks, with the day (for example `` `1a2b3c4` (2026-11-17) ``), in the field "Compared" of the record and each difference in "Differences" ("None" if there is none).
- The gate reads the records. A mockup in the state Built must name a commit in "Compared" and at least one screen. When a row names a commit, the gate fails if a Svelte or CSS file below one of its screen folders changed after that commit. Then compare again and write the new commit. Name a commit of `main`: a commit of a branch that was squashed does not exist in a different clone, and the gate fails there. The gate reads commits, so it fails in the first gate run after the commit that changed the screen, which is the run before the merge. The gate does not see a layout that is in `apps/client/src/lib/`: put the folder of the component in "Screens" too.
- The first comparison of each row is open. Until it is made the row says "Not compared", and the gate cannot find a difference for that row.
